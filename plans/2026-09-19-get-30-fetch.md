# GET-30 Firecrawl fetch replacement

## Corrected issue evidence

The first Linear read returned only the title and led to the already-merged
multi-source contact-fetch slice in PR #203. Post-merge readback exposed the
actual issue body: replace the static `fetch_web` implementation with
Firecrawl so JavaScript pages, PDFs, anti-bot pages, and clean Markdown are
supported, and remove the product-runtime dependency for running the Agent.
PR #203 is useful adjacent work, but is not sufficient acceptance for GET-30.

## Outcome

Route governed same-Run `fetch_web` reads through Firecrawl v2 while preserving
the existing discovery handle, authorization, provenance, cancellation, and
zero-external-effect boundaries. Keep the standalone Agent command runnable
without the Talent Signal product runtime.

## Firecrawl boundary

- Only the exact public HTTPS URL discovered by `search_web` in the same Run
  may be sent to Firecrawl; arbitrary URL input remains forbidden.
- Request only main-content Markdown with PDF parsing and bounded timeout.
- Send no browser cookies, private headers, conversation content, or product
  credentials. Disable provider caching. Request zero data retention only when
  the configured Firecrawl account has that capability; never claim it from an
  anonymous or unverified account.
- Reject API failures, non-success target status, empty/oversized Markdown,
  and substituted source URLs before the result can become evidence.
- Keep the search provider identity on the fetched evidence and hash the exact
  normalized Markdown returned by Firecrawl.
- Require `FIRECRAWL_API_KEY` only in the Agent Host secret boundary. The API,
  Web, iOS, and model prompt never receive the credential; standalone means no
  product runtime dependency, not credential-free provider access.

- the standalone `agent:research` path remains independent of backend/Web/iOS;

## Firecrawl implementation and local verification

- The default general-research gateway now requires an explicit fetch adapter;
  the CLI wires it to the fixed Firecrawl v2 scrape endpoint instead of the
  legacy static HTML fetcher.
- The adapter validates the search provider, authorization domain, public DNS,
  exact returned URL, provider status, target status, bounded Markdown, and
  caller cancellation before creating evidence.
- Provider caching is disabled. An anonymous smoke succeeded for
  `https://example.com` but a real standalone Run against the official docs was
  rejected by Firecrawl for anonymous access, so the production path requires
  a key and fails closed at startup. ZDR produced an explicit provider
  capability error and therefore remains an opt-in flag, never an implied
  claim.
- `pnpm agent:check` passed: Agent 269 passed / 1 skipped; Agent Host 80 passed.
  Secret-manifest tests, documentation/wiki/architecture checks, typechecks,
  builds, and whitespace checks passed.
- Infisical readback now has the explicit Exa search-provider selector, but
  `FIRECRAWL_API_KEY` is still missing from `dev:/agent-host`. The fail-closed
  contract correctly reports that one missing name. A credentialed live Run
  remains the external acceptance blocker; GET-30 must not be treated as
  complete until the key is supplied and the Run is re-read successfully.

## Adjacent work already delivered in PR #203

Let one authorized contact-research tool call read several sources discovered in
the same task without losing source identity when one page is unavailable or
belongs to a provider that cannot supply page content.

## Boundary

In scope:

- `fetch_contact_source` accepts an ordered, unique list of at most five exact
  same-task source references;
- Exa content reads are combined into one bounded provider request;
- every requested source receives an explicit success or bounded failure
  outcome, in request order;
- fetched content preserves the discovered source identity, channel, content
  hash, retrieval time, and provider receipt;
- TikHub profile observations never fall through to Exa; they remain usable as
  discovery observations and require the existing isolated browser tool when
  rendered page content is necessary;
- partial success remains visible to the Agent and durable task observation.

Out of scope:

- cookies, authenticated profiles, private pages, arbitrary URLs, automatic
  identity binding, provider fallback, or external profile writes;
- batching the JavaScript browser path;
- treating search snippets or profile observations as fetched evidence.

## PR #203 original evidence assumption

- GET-30 contains only the title `优化 fetch 的逻辑`; there is no issue body or
  acceptance checklist.
- Merged GET-31 upgraded search to a multi-channel v2 contract, but fetch still
  accepts one source per model turn and invokes Exa regardless of the source's
  discovery provider.
- That path can send a TikHub-discovered URL to Exa, change provider/source
  identity, and fail the whole tool call without a per-source receipt.
- Exa's existing contents request shape already accepts a URL list, while the
  adapter artificially wraps only one URL.

## Approach

1. Upgrade the contact-research contract with bounded multi-source fetch input
   and ordered per-source outcomes.
2. Add a bounded Exa batch contents adapter and keep the single-source helper
   as a compatibility wrapper where still useful.
3. Resolve every short reference inside the durable task before dispatch,
   retain only schema-checked successful reads, and record partial limitations.
4. Cover batching, order, missing content, provider mismatch, cancellation,
   bounds, persistence, and citation continuity with focused tests.
5. Run independent safety review, latest-head CI, merge, and Linear readback.

## PR #203 completion evidence

- one test proves several Exa URLs produce one contents request and ordered
  results;
- mixed Exa/TikHub input preserves Exa success and returns an explicit TikHub
  unsupported outcome without sending that URL to Exa;
- malformed, duplicate, foreign, or excessive source references fail before
  provider dispatch;
- backend integration proves short references resolve and fetched sources stay
  citeable by their original source identity;
- all affected package tests/typechecks and repository gates pass on the latest
  PR head; the PR is merged before GET-30 is completed.

## Implemented

- `contact-research-tools.v3` accepts one to five ordered, unique resolved
  sources and returns a strict outcome for every requested source.
- Exa sends one bounded `/contents` request, ignores substituted provider
  results, restores request order, and leaves missing pages as explicit
  per-source failures.
- TikHub and browser sources never cross into Exa. Their unsupported text-fetch
  outcome is explicit; rendered social content stays on the isolated browser
  path.
- Successful reads preserve the original source ID and channel while updating
  the page text, content hash, retrieval time, and provider receipt.
- The backend resolves all short references before dispatch, persists partial
  results and limitations, and rejects any Agent Host response whose outcomes
  or successful sources do not exactly match the request.
