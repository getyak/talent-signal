# Primary-login WK store ownership: proposal review

**Conditionally sound.** A fresh persistent WK data store can isolate late A `Set-Cookie` from B, including after restart. However, an in-memory coordinator that serializes only native login, plus saving B's identifier after success, is insufficient. The minimum complete design needs durable store ownership, retirement of every old host, and coverage of other writers of the same session cookie. This is a proposal review, not implemented or real-WK acceptance.

## Minimum ownership protocol

1. **One coordinator per selected origin/store, shared by all hosts.** A lease identifies `{origin, storeID, storeEpoch, hostID, operationID}`. Acquire it before admitting a primary-login flow; only its captured host may dispatch the session-writing exchange. Do not queue an already-prepared B with A's cookie fingerprint: after admission B must start again from the first-party entry. Backend scope/PKCE/state checks remain authoritative. Credential rounds keep their existing store and authorization; if a primary identity transition retires that store, retire their old hosts too rather than silently transferring proofs.
2. **Persist uncertainty before dispatch.** Maintain a small native registry, keyed by canonical origin: active UUID/epoch and an unresolved primary-login marker. Commit that marker durably before a request that may install a session. Persist quarantine plus the newly selected UUID/epoch before constructing/loading B. On restart, an unresolved marker means the old store cannot become the authentication-write destination again. A crash between commit and receipt, a missing window, timeout, invalid receipt or failed cleanup is not evidence of zero cookie effects. A plain asynchronous preferences update or a timeout-based lease release does not prove this ordering. If persistence fails, do not dispatch. Handle a damaged previously initialized registry explicitly; never silently choose the old deterministic UUID.
3. **Retire the whole store epoch.** On explicit abandonment after possible dispatch or lost ownership, detach/freeze every old host, stop further navigation and invalidate old callbacks. Create all replacement hosts with the selected UUID. Late A may change only quarantined A's store; it must never change the registry, release B's lease, clear B's recovery, or navigate B. Process startup and origin changes consult the same registry. Either enforce one app process owns it or use an OS-backed cross-process lock; a `@MainActor` singleton alone covers only one process.
4. **Settle only what was observed.** An exact accepted login response plus same-jar authenticated readback can establish installation of that login. A backend `committed` result alone cannot establish that its original HTTP response has arrived. Cancel-render, `stopLoading`, navigation cancellation, window destruction and elapsed TTL are not cookie rollback or proof that no response remains. Before allowing a later identity-changing login in the same store, every older session-cookie writer must be known settled. Otherwise choose a fresh store.
5. **Keep rotation small and explicit.** Store identifiers are local routing metadata, not account IDs or server authorization. Store no bearer tokens/verifiers in the registry and copy no cookies, local storage or secrets. Quarantine does not revoke an already-created backend session or undo a mutation. Preserve unresolved-outcome wording. Do not delete quarantined stores during recovery; later bounded cleanup may use WebKit's removal API only after their views are released. Never auto-select an old UUID from enumerated stores.

## Scope correction and narrower implementation choice

The candidate closes the specific A-native-consume/B-native-consume race **if both writers obey that lease and every unresolved restart selects a fresh jar**. It does not close all primary-session races while password login, logout, OAuth callbacks or JWT refresh can still write independently to the same jar.

Avoid a generic profile manager or backend session schema. Reuse the existing origin-based store for steady workspace use; add only an active UUID override/epoch and durable uncertainty record. Adopt the existing deterministic UUID once during migration to preserve the installed session. For a later explicit primary-login transition, prefer a fresh store **before the first-party login page/proof begins whenever old writers cannot be proven quiescent**. This also isolates stale refresh/logout responses without trying to intercept every fetch in WKNavigationDelegate. A password form must begin in that selected store before credentials are entered; never capture/replay its POST into another jar. The normal workspace and credential-setting flows do not rotate stores routinely.

If the parent elects to keep the same jar for a subsequent primary login, all session-writing paths need enforceable admission/settlement, including fetch-based Auth.js session responses. Merely disabling provider buttons or observing main-frame navigation is not that enforcement. An indefinite same-jar block is smaller but does not meet the requested usable abandonment/restart recovery; ephemeral stores would give up persistence. The conditional UUID rotation is the smallest complete alternative found here.

## Required real-WK acceptance

Use controlled first-party responses and disposable identified persistent stores; record HTTP requests, safe store/operation identifiers and server-authenticated actor readback, never real cookie values. These cases have **not** been run in this review.

1. **Shared-store admission:** two WKWebViews with the same identifier; hold A after backend success but before response headers. B's session-writing request must not reach the server in that store. Cover same-window restart and a second window. Then release A and verify the exact terminal transition/readback before reuse.
2. **Quarantine ordering:** abandon held A, durably choose fresh B, finish B, release A. Verify A actually receives its late cookie in old store while real same-origin requests from every active B host still authenticate B. Repeat with held old JWT-refresh and logout responses, not only native consume. An ignored native receipt alone is insufficient.
3. **Crash/relaunch:** terminate at the boundaries before/after uncertainty persistence, after backend commit before headers, after headers before native receipt, and after new UUID persistence before B success. Relaunch must select only the recorded safe epoch; unresolved old stores never re-enter. If the old socket cannot deliver after termination, report that limit rather than claiming a delivered late-response test. Also test second-process ownership or its explicit rejection.
4. **Stale host/origin:** close A, switch away/back, reconnect the same origin, reopen Settings and activate old callbacks. None may reselect A or clear B. Recreate a second WK view with B's remembered UUID after restart and verify its session; another port/origin must retain its independent selection. Exercise registry-write failure and missing/damaged initialized state.
5. **Boundaries retained:** ordinary password/provider logins begin in the selected jar; current/target credential proof and contacts/session readback remain in the canonical active jar. Invalid receipt/network loss preserves ambiguity; known pre-write cancellation does not unnecessarily destroy a healthy store. A fresh store does not promise recovery of unsent local-only drafts from quarantine; keep that data protected and communicate the consequence before explicit abandonment.

## Exact ADR0021 adjudication

Read-only review of `/Users/cubxxw/data/talent-signal-account-sync/docs/decisions/0021-primary-login-store-ownership.md`, SHA256 `0ae0ed43af8eb6b584705f8d88bc01bba3b9b60efd665e9329543a91e5a62e63` (uncommitted local candidate at review time).

The design is consistent with the bounded store-isolation evidence. Marking uncertainty before exposing a login form (`63–70`), defaulting later primary entry to a fresh store (`39–45`), prohibiting prepared/password replay, requiring durable atomic selection and process ownership, reconstructing all hosts by epoch, and preserving quarantined drafts are all explicit. No further profile system or backend schema is needed. Two consumer seams should be stated explicitly before freezing implementation instructions; these are design clarifications, not new dynamically reproduced product defects:

1. **Admission inside the login page:** `47–49` permits validation retries before a possibly committing request, while `64–65` correctly notes native cannot observe every fetch. The durable entry marker protects crash recovery but cannot itself stop two password/provider submissions inside that entry. Require synchronous single-flight admission across the login page's methods and all hosts before a request is sent; after possible dispatch, freeze other identity submissions until a definitive zero-effect response or explicit fresh-store restart. Do not infer this solely from navigation callbacks. Acceptance should rapidly submit A, attempt B/another provider while A is held, and verify that no second session writer reaches the same jar. This does not require native access to a password.
2. **A truly non-writing status consumer:** `77–83` should require `Cache-Control: no-store`, no `Set-Cookie` and live backend-session validation, rather than merely decoding an unexpired JWT. The installed Auth.js `/api/auth/session` refreshes the session cookie and therefore is not automatically a suitable read-only substitute. Match status to the active lease/store epoch; its positive result establishes the session observed in that jar, not that every earlier response has drained. Where native cannot observe a password fetch's actual completion, do not use a status success to authorize another potentially identity-changing write in that same jar. Preserve the default fresh-store rule for a new primary flow. Test revoked-session status, late old status after epoch replacement, and zero cookie mutation on success/failure.

Implementation note for the already-required OS lock: hold a stable lock identity independently of the atomically replaced journal file; locking an inode and then replacing that inode does not protect later openers of its pathname. Verify this through the specified second-process contention test. This is a narrow implementation constraint, not a request for another storage system.

The parent owns the ADR. This adjudication does not modify it or waive app-level acceptance.
